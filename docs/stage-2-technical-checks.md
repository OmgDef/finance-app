# Этап 2. Доступ и окружение TэтаФинанс

13 ноября 2026 года. **Три оставшиеся мобильные проверки этапа 2 пройдены на локальной VM и двух эмуляторах.**

## Что входит в этап

- npm workspaces с общим lockfile, GitHub Actions и Docker Compose. На локальной VM Caddy обслуживает мобильное API и админку на отдельных HTTPS-портах одного IP. Fastify проверяет адрес с портом и HTTPS, а для определения IP доверяет адресу Caddy во внутренней сети. MySQL и Fastify работают без публикации портов на хосте.
- [Единый контракт API](../packages/contracts/src/index.ts) задаёт маршруты, схемы запросов и ответов, клиентские типы и генерацию OpenAPI 3.1. [Миграция](../apps/api/migrations/0000_access.sql) создаёт схему доступа, публичной поддержки и аудита, включая статус `review` для восстановленного аккаунта.
- Мобильный клиент на Expo Router и админка на Vite поддерживают EN/RU и сохраняют выбор языка. В админке доступны настройка TOTP, вход, создание аккаунта, одноразовый показ кода, отзыв телефона и изменение статуса. Мобильное приложение получает контакты до активации и профиль после входа.
- Проверочные значения и токены используют HMAC-SHA-256 с разграничением по назначению. PIN дополнительно хэшируется Argon2id с индивидуальной солью. Пароль администратора хранится с Argon2id, секрет TOTP шифруется AES-256-GCM отдельным ключом. iOS хранит маркер установки в Application Support с исключением из резервной копии, Android — в `noBackupFilesDir`. [Node.js Crypto](https://nodejs.org/api/crypto.html), [Expo SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/), [Expo ScreenCapture](https://docs.expo.dev/versions/latest/sdk/screen-capture/)

## Стенд на локальной VM

- Мобильный API — `https://192.168.139.211:18443`. Админка и административное API — `https://192.168.139.211:18444`. Caddy слушает IP VM. Fastify и отдельная синтетическая БД MySQL слушают loopback VM на `3000` и `13306`.
- На VM прошли чистая установка npm, сборка админки и OpenAPI, первая и повторная миграции, 9 интеграционных проверок. На HTTPS проверены разрешённые и перекрёстные маршруты, отказ при подстановке `Host` другого порта, отказ административному запросу с Origin мобильного порта и проверка цепочки сертификатов. Chrome выполнил настройку TOTP, вход, выдачу кодов и выход на административном порту. Release-сборки iOS и Android получили контакты до входа, активировались этими кодами и показали профиль напрямую через VM при выключенном Metro. Android прошёл без `adb reverse`. При смене `EXPO_PUBLIC_API_ORIGIN` пришлось принудительно пересобрать Hermes-бандл, поскольку Gradle сохранил прежний адрес.
- Стенд работает отдельными пользовательскими службами `tetafinance-stage2-db`, `tetafinance-stage2-api` и `tetafinance-stage2-caddy` из `/home/def/tetafinance-stage2`. На VM проверены Node.js `26.13.1`, npm `11.20.0`, Caddy `2.11.9` и MySQL `8.4.13-0ubuntu0.26.04.2`. Службы включены в пользовательский автозапуск, после их перезапуска HTTPS проверен повторно. Состояние доступно через `orb -m ubuntu systemctl --user status tetafinance-stage2-api tetafinance-stage2-caddy tetafinance-stage2-db`. Предыдущий стенд на Mac остановлен, его Docker-тома сохранены.
- Вложенный Docker `29.1.3` и Compose `2.40.3` установлены на VM. Overlayfs завершился с `operation not permitted`. VFS запустил тестовый контейнер, но Compose остановился на загрузке образа MySQL, а импорт локального образа вернул `operation not permitted`. Схема прошла `docker compose config --quiet`, Caddyfile — `caddy validate`. Рабочий прогон VM выполнен через нативные службы.

## Как повторить

Скопируйте публичный CA действующего стенда в локальный файл и добавьте доверие только в тестовый клиент.

```sh
orb -m ubuntu cat /home/def/tetafinance-stage2/caddy-data/caddy/pki/authorities/local/root.crt > /tmp/teta-local-ca.crt
curl --cacert /tmp/teta-local-ca.crt https://192.168.139.211:18443/api/v1/health
```

Чтобы создать администратора на действующем стенде, выполните в оболочке VM из `~/tetafinance-stage2/app` команду ниже. Она принимает пароль через stdin. Полученный секрет используйте в форме настройки TOTP.

```sh
~/tetafinance-stage2/runtime/node-v26.13.1-linux-arm64/bin/node \
  --env-file="$HOME/tetafinance-stage2/api.env" apps/api/src/operator.ts admin@example.test < /path/to/password-file
```

Для локального запуска через Docker Compose скопируйте [шаблон окружения](../infra/.env.example) в `infra/.env`, задайте разные 32-байтные случайные ключи и отдельные пароли MySQL в hex. Compose по умолчанию публикует API на `http://127.0.0.1:18443`, а админку на `http://127.0.0.1:18444`. IP и порты задаются в `TETA_BIND_IP`, `TETA_API_PORT` и `TETA_ADMIN_PORT`. На мобильном порту Caddy убирает `Cookie` из запросов к API и `Set-Cookie` из ответов.

```sh
docker compose -p teta-local --env-file infra/.env -f infra/compose.yaml up --build -d
curl -fsS http://127.0.0.1:18443/api/v1/health
```

Для локальной мобильной dev-сборки задайте `EXPO_PUBLIC_API_ORIGIN=http://127.0.0.1:18443`. На Android выполните `adb reverse tcp:18443 tcp:18443`. Для повторения HTTPS-проверок на локальном Compose задайте `TETA_SCHEME=https` и добавьте CA Caddy в доверие тестового клиента.

За nginx задайте в API два публичных HTTPS-адреса в `API_ORIGIN` и `ADMIN_ORIGIN`, а в `PROXY_IP` укажите адрес, с которого nginx подключается к Fastify. В блоках проксирования передавайте исходный `Host` через `proxy_set_header Host $http_host;`, схему через `proxy_set_header X-Forwarded-Proto $scheme;` и адрес клиента через `proxy_set_header X-Forwarded-For $remote_addr;`. Fastify принимает внутреннее HTTP-соединение от nginx. [Документация nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header)

Команда [оператора](../apps/api/src/operator.ts) принимает email аргументом, пароль по stdin и выводит одноразовый секрет восстановления. Выполните `node apps/api/src/operator.ts <email>` в контейнере API и откройте «Настроить или восстановить доступ» на административном хосте. Для входа после настройки TOTP дождитесь следующего 30-секундного кода. `npm test` запускает интеграционные проверки при наличии `TEST_DATABASE_URL` к мигрированной синтетической БД. Для мобильной сборки на стенде задайте `EXPO_PUBLIC_API_ORIGIN=https://192.168.139.211:18443`. Для iOS добавьте CA стенда в выбранный симулятор. Для Android используйте тестовую конфигурацию доверия к CA для адреса стенда. Предыдущие мобильные прогоны шли через HTTPS на `localhost` с доверенным тестовым CA и `adb reverse` на Android. Контакты на экране активации загружаются из админки. При первом запуске без сети контакты скрыты.

Нативные команды из каталога `apps/mobile` после `expo prebuild --no-install` и настройки тестового HTTPS. Для iOS сначала выполните `pod install` из `ios` под CocoaPods 1.16.2. В прогоне для Keychain подписали сборку Xcode с тестовыми `application-identifier` и `keychain-access-groups` в сгенерированном проекте симулятора. Android использовал JDK 21 и тестовую подпись Gradle.

При чистой генерации текущего проекта Expo создаёт `TetaFinance.xcworkspace` и схему `TetaFinance`. В проекте, сгенерированном для этого прогона, оба имени были `TetaFinans`.

```sh
xcodebuild -workspace ios/TetaFinance.xcworkspace -scheme TetaFinance \
  -configuration Release -sdk iphonesimulator -destination 'generic/platform=iOS Simulator'
cd android
# При смене EXPO_PUBLIC_API_ORIGIN
./gradlew :app:createBundleReleaseJsAndAssets --rerun -PreactNativeArchitectures=arm64-v8a
./gradlew :app:assembleRelease -PreactNativeArchitectures=arm64-v8a
```

## Мобильная приёмка на VM

В iOS Simulator (iPhone 17 Pro, iOS 26.5) и Android Emulator (Pixel 9, Android 15) использовали отдельные Release-установки с синтетическими аккаунтами. Коды выдали через HTTPS-админку. Временный HTTPS-порт проксировал запросы к штатному API. Экран проверяли через Maestro, состояние кодов и устройств — в MySQL.

| Проверка | Результат |
| --- | --- |
| Отказ записи секрета в SecureStore | На каждой платформе нативный модуль тестовой сборки один раз отклонил запись ключа `installation`. Новый телефон показал ошибку хранения и остался на активации. Запрос активации не поступил на VM. В MySQL сохранились активное устройство и действующий код, число устройств и событий `activation.used` не изменилось. Старый телефон вошёл по PIN. Повтор на новом телефоне с тем же кодом создал ровно одно устройство и одно событие `activation.used`, после чего прежний телефон получил отказ. |
| Запоздавший ответ `/me` | VM получила `200` от API до истечения 7-секундной сессии и отправила ответ клиенту через 1,8 секунды после истечения. Экран PIN появился до доставки ответа. После доставки на обоих устройствах экран PIN оставался видимым, а заголовок профиля и email отсутствовали. Вход по PIN вернул профиль. |
| Истечение сессии при открытом приложении | Для каждого синтетического токена установили одинаковый срок в БД и в выданном клиенту `expiresAt` (75 секунд). Профиль был виден до истечения, затем в том же процессе без ухода в фон открылся экран PIN. Отдельный запрос к API со старым токеном вернул `401 SESSION_EXPIRED`. Вход по PIN выдал новую сессию и вернул профиль. |

Флаг запуска тестовой сборки заставлял нативный модуль SecureStore вернуть ошибку перед записью. Для Android модуль собрали из исходников. После прогона временный порт закрыли, доступ шести синтетических аккаунтов отозвали, а оба штатных HTTPS-порта проверили повторно.

## Оставшаяся приёмка

- Доступ к Ubuntu 26.04 LTS ARM64 подтверждён через локальный OrbStack. Прямой SSH ожидает подтверждения ключа хоста. Рабочие имена, DNS и внешний доступ входят в этап 6.
- На этапе 3 повторить сценарий запоздавшего ответа на первом финансовом экране. Получить успешный ответ с синтетическими финансовыми данными до блокировки, доставить его после блокировки и проверить, что данные остаются скрытыми до нового входа.
- Рабочие контакты задаются в админке. На локальном стенде заполнение проверено на синтетических контактах. При первом запуске без сети контакты скрыты. Редактирование FAQ и контактов реализовано на этапе 5.
- Аппаратная биометрия, подпись физических устройств и системное доверие к сертификатам рабочих хостов относятся к этапу 6.
