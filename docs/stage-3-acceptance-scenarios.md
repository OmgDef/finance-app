## Подготовка данных

- Каждый сценарий и каждый порядок гонки начинаются с отдельного набора синтетических данных. По умолчанию владелец `U` активен, зона профиля `Asia/Makassar`, счёт `A` активен, валюта EUR, начало учёта `2027-01-01`. `B` и `D` принадлежат тому же владельцу, если указаны в примере. `V` — другой пользователь, `M` — администратор с доступом к данным `U`. Категории доходов и расходов существуют. Указанный начальный остаток входит в журнал. Правила и операции задаются в каждом примере.
- Все суммы в строках минимальных единиц. Например, `"100000"` соответствует 1 000,00 EUR. Моменты с `Z` заданы в UTC. Часы сервера и обработчика фиксируются на указанных моментах. Версии читаются из предпросмотра или актуального состояния. После изменения сравниваем их с исходными значениями.
- Для гонок открываем два соединения MySQL. Приостанавливаем первую транзакцию с захваченной блокировкой, запускаем вторую и подтверждаем, что она ожидает ту же блокировку. Затем даём первой завершиться. Для гонки с обработчиком фиксируем выбор кандидата до захвата блокировки. Каждый порядок из сценария проверяем на исходных данных.
- После каждого шага сверяем ответ API и состояние через отдельное чтение после фиксации или отката. Проверяем остатки по актуальным движениям, версии и историю, итог ключа, финансовый аудит и состояние дат, если сценарий их затрагивает. Количество записей считаем относительно исходного состояния. Для ошибок, которым план ещё не назначил код, проверяем описанный результат команды и состояние данных.

Для тестов фонового обработчика примените миграции к отдельной синтетической схеме без правил и передайте её адрес в `TEST_WORKER_DATABASE_URL` при запуске `npm test`. `TEST_DATABASE_URL` используется остальными интеграционными тестами.

## Закрытие команд после потери ответа

Для КМ-01–КМ-05 `A` имеет `"100000"` на `2027-02-01T04:00:00Z`. Команда с ключом `K1` записывает расход `"10000"` за `2027-02-01` на счёте `A`. `K1` и `K2` — разные ключи текущей версии восстановления. Субъект `U`, владелец данных `U`. Клиент до отправки сохраняет ключ, вид команды, субъект, владельца и ID существующего объекта. После перезапуска доступны эти данные, тело запроса потребуется ввести заново, если закрытие разрешит повторную отправку. Статус и закрытие вызываются через `/api/v1/commands/status` и `/api/v1/commands/close`.

| Сценарий | Вход и порядок действий | Ожидаемый результат |

## Замена правила графика

`A` начинается с `"100000"`, второй активный счёт `B` в EUR с `"50000"`, начало учёта `B` — `2027-01-01`. Правило `R` из СВ-01 списывает `"10000"` с `A` по понедельникам с `2027-02-01`. 31 января в `04:00Z` сверка до `"90000"` сохраняет досрочный пропуск `R` за 8 февраля. Обработчик пока выключен, 1 февраля ждёт проведения. В `2027-02-01T04:00:00Z` заменяем `R` с его актуальной версией. Новое правило `S` списывает `"7000"` с `B` по вторникам со 2 февраля, последняя дата `2027-02-16` включительно. Решение для 8 февраля — перенести пропуск на 9 февраля в `S`.
