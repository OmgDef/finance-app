# Резервное копирование и восстановление TetaFinance

Цели MVP для отказа хоста — RPO до 24 часов и RTO до 4 часов с регистрации инцидента. Перед вводом в работу владелец подтверждает цели, время реакции оператора, место хранения копий и канал оповещений. Репетиция проводится на изолированной схеме. Оператор сохраняет время точки снимка и регистрации инцидента, время готовности API, успешного повторного входа пользователя и первой подтверждённой проводки обработчика.

## Копия

1. Создайте MySQL-файл параметров с секцией `[client]` для источника. Храните файл с правами `0600` и используйте доступ к одной схеме. Подготовьте отдельный файл со случайной парольной фразой GnuPG из защищённого хранилища. Разместите ключ и серверные `ACCESS_KEY` и `TOTP_KEY` отдельно от копий. Подготовьте их получение для дежурного оператора и проверьте, что он может прочитать копию после потери рабочего хоста. Храните образ приложения, исходники миграций и настройки запуска по идентификатору версии.
2. Запускайте выгрузку каждые 12 часов. Согласованный снимок использует транзакцию InnoDB. На время выгрузки остановите миграции и другие изменения схемы. Обычные транзакции приложения могут продолжаться. Запускайте скрипт в Linux с `mysql`, `mysqldump`, `gpg` и GNU coreutils.

   ```bash
   bash infra/recovery-backup.sh dump "$MYSQL_CNF" "$SOURCE_SCHEMA" "$PASSPHRASE_FILE" "$ARTIFACT.gpg"
   ```

3. Скрипт проверяет расшифровку с контролем целостности. Перенесите `.gpg` и `.gpg.sha256` во внехостовое хранилище и сверьте SHA-256 полученного файла. Вместе с копией запишите идентификатор версии и выведенную отметку UTC, снятую непосредственно перед запуском `mysqldump`. Эта отметка даёт консервативное начало интервала возможной потери. После проверки копии запишите её как последнюю проверенную. Сбой выгрузки, шифрования, копирования или проверки должен сразу вызвать оповещение. Отдельная проверка должна оповестить оператора, когда последняя проверенная копия старше 12 часов. При ошибке выполните повтор с новым именем файла и проверьте обе части результата.
4. Для контроля восстановления периодически импортируйте проверенную копию в пустую отдельную схему. Скрипт проверяет SHA-256, полностью проверяет расшифровку до импорта и передаёт расшифрованный SQL прямо в MySQL. При частичном импорте удалите только неудачную изолированную схему и повторите с новой пустой схемой.

   ```bash
   bash infra/recovery-backup.sh restore "$RESTORE_MYSQL_CNF" "$RESTORE_SCHEMA" "$PASSPHRASE_FILE" "$ARTIFACT.gpg"
   ```

## Инцидент и открытие доступа

1. Зафиксируйте `INCIDENT_UTC`, закройте входящий доступ и остановите API и worker. Сохраните журналы и записи решений с отдельного носителя. Подготовьте новую схему с нужными кодировкой, настройками MySQL и правами пользователя приложения. Восстановите копию и проверьте число и версии миграций, счета, остатки, движения, версии операций, правила и позиции графика, аудит и результаты команд. Сравните с доверенной сверкой для этого снимка. Сохраните проверенный результат до внесения решений. Примените миграции выбранного релиза при остановленных процессах и проверьте журнал миграций перед подготовкой доступа.
2. Подготовьте подтверждённый владельцем список действующих администраторов. В файле укажите по одному логину на строку. Список должен содержать минимум одного администратора, включённого в восстановленной БД. Если в снимке отсутствует действующий администратор, сначала создайте его локальной процедурой `admin:configure` при закрытом доступе, затем внесите в список. Внешний журнал операций хранит последнюю использованную версию восстановления. Назначьте целое `RECOVERY_VERSION` от 2 до 9999999999, больше любого ранее выданного значения для этого сервиса, включая версии после снимка. В обоих окружениях, для оператора и для сервисов, укажите URL восстановленной БД.

   ```bash
   node --env-file="$OPERATOR_ENV" apps/api/src/recovery-operator.ts prepare \
     "$RESTORE_SCHEMA" "$SNAPSHOT_UTC" "$INCIDENT_UTC" "$ADMIN_ALLOWLIST"
   ```

   Транзакция отзывает старые установки, биометрию, коды и сессии, завершает старые шаги входа и настройки TOTP, очищает выданные секреты восстановления TOTP, отключает остальных администраторов, отправляет все восстановленные аккаунты на проверку, удерживает существующие правила и сбрасывает heartbeat и курсор worker. Аудит фиксирует интервал и переходы. Остатки, движения, история и результаты команд остаются в состоянии снимка. При неопределённом результате `prepare` проверьте `SELECT version, snapshot_at, incident_at, prepared_at FROM recovery_state`. Эта запись появляется только при завершённой транзакции. Успешная подготовка с той же версией повторно отклоняется.
3. Сверьте реквизиты разрешённых администраторов. При сомнениях сбросьте их пароль и TOTP через локальную процедуру `node --env-file="$OPERATOR_ENV" apps/api/src/operator.ts "$ADMIN_LOGIN"`. Передайте новый пароль по stdin и передайте единственный выведенный секрет защищённым каналом. Держите запуск в изолированном контуре и выполните настройку TOTP, затем новый вход. API и worker проверяют точное соответствие `RECOVERY_VERSION` записи в БД перед запуском. Для обычной БД, где `recovery_state` пуста, версия равна `1`.
4. Откройте административный доступ только подтверждённым операторам. Сверьте, что старые установки, коды, сессии и шаги отклоняются. В админке проверьте каждый аккаунт по записям после снимка или явному подтверждению владельца сервиса. Укажите источник и причину в форме проверки. Сохраните известные блокировки. Аккаунты без подтверждения оставьте в ожидании. Контрольно выпустите новый код подтверждённому активному пользователю, выполните активацию и разблокировку новым устройством. Проверьте, что по старому ключу сохраняется известный результат, а статус, закрытие и запись неизвестной команды возвращают `COMMAND_REQUIRES_REVIEW`. Сообщите затронутым пользователям границы интервала возможной потери и порядок ручной сверки.
5. До запуска worker сопоставьте ожидавшие обработки даты на момент снимка, даты до инцидента и сведения о правках проведённых записей. Используйте экран графика по каждому владельцу и диапазону дат, затем историю связанных операций и журнал решений. Восстановите известную отмену через административный предпросмотр и подтверждение отмены с причиной. Проверьте новую версию операции и прежний исход даты, чтобы исключить повторное автопроведение. Для сомнительной проведённой записи пометьте счёт на сверку. Для спорной непроведённой даты в удерживаемом правиле назначьте ручную проверку. Оставьте правило удерживаемым, пока есть сомнения в его параметрах. Освободите каждое проверенное правило отдельным решением.

   ```bash
   printf '%s\n' "$REASON" | node --env-file="$OPERATOR_ENV" apps/api/src/recovery-operator.ts flag-account \
     "$RESTORE_SCHEMA" "$ACCOUNT_ID"
   printf '%s\n' "$REASON" | node --env-file="$OPERATOR_ENV" apps/api/src/recovery-operator.ts flag-date \
     "$RESTORE_SCHEMA" "$RULE_ID" "$FINANCIAL_DATE"
   printf '%s\n' "$REASON" | node --env-file="$OPERATOR_ENV" apps/api/src/recovery-operator.ts release-rule \
     "$RESTORE_SCHEMA" "$RULE_ID"
   ```

   Причина содержит ссылку на запись решения или краткое основание без реквизитов доступа. Дата с `RECOVERY_UNCERTAIN` требует решения администратора с причиной и текущей ревизией. После освобождения правила она остаётся на ручной проверке. Статус входа владельца и проверка графика независимы. Удерживаемые правила не попадают в очередь worker.
6. Проверьте `/api/v1/health` через HTTPS и повторный вход. Запустите worker, подтвердите свежий `schedule_worker_state.last_success_at` и отсутствие проводок по удерживаемым и спорным датам. Сверьте новую проводку по проверенному графику. После контрольных проверок откройте пользовательский HTTPS и запишите время восстановления. При дежурстве контролируйте ошибки API и `schedule_worker_pass_failed`, свободное место `df`, возраст проверенной копии, возраст `last_success_at` и задержку старейшей наступившей даты в `oldestDueLagMs` отчёта worker. Worker запускает проход раз в минуту. Удержанные правила и даты для вмешательства дополнительно сверяйте по административному списку. Порог и получателя оповещений согласуйте перед рабочим запуском.

## Откат

При сбое до открытия остановите worker и API, сохраните изолированную копию результатов и возобновите работу по журналу решений. Если частично импортировали или ошиблись схемой, повторите импорт из проверенного шифротекста в новую пустую схему и назначьте версию по внешнему журналу. В рамках уже подготовленной базы сохраняйте зафиксированную версию при перезапусках. После выдачи новых ключей и открытия доступа дальнейшее восстановление требует новой версии и сверки изменений после открытия.

На обычной базе миграция `0017` добавляет поля и таблицу с безопасными значениями по умолчанию. Для отката приложения сохраните схему и журнал миграций. На восстанавливаемой базе используйте только API и worker с проверкой версии и поддержкой удержания. Старая версия worker не знает об удержанных правилах и может провести спорную дату. При откате на предыдущий образ оставьте доступ и worker закрытыми и сохраните подготовленную схему. Проверьте совместимую версию отдельно перед подключением.

Миграция `0020` сохраняет регистрации и сессии, но удаляет поле, через которое предыдущий API выбирал единственное устройство. Остановите старый API перед применением миграции. После неё используйте версию API и инструмент подготовки восстановления с поддержкой нескольких устройств.

На локальной VM отдельно проверили обычную схему `0017` без незавершённого восстановления. Текущий API записал расход 20 EUR, API из версии до `0015` вернул прежний результат по тому же ключу, а предыдущий worker провёл наступивший расход 10 EUR. После возврата к текущим процессам осталось два движения и один проведённый итог даты. Остаток составил 470 EUR. Для одновременной работы тестовых служб предыдущий API запускали на отдельном loopback-порту.

## Воспроизведение репетиции

Подготовьте две пустые схемы `teta_drill_source[_суффикс]` и `teta_drill_restored[_суффикс]` в локальном MySQL. Суффикс использует строчные латинские буквы и цифры. Укажите их URL через `DRILL_SOURCE_URL` и `DRILL_RESTORED_URL`, только на `127.0.0.1`. Укажите `DRILL_MYSQL_CNF` для доступа к обеим схемам, `DRILL_KEY_FILE` для отдельного файла с парольной фразой, путь к Caddy через `DRILL_CADDY` и две новые директории `DRILL_WORK_DIR` и `DRILL_BACKUP_DIR`. В локальной VM каталог архива может быть общей папкой хоста, а ключ остаётся в VM. Установите зависимости проекта и используйте Node 26. Репетиция запускает Caddy и реальные процессы приложения на loopback-портах `18843`, `18844` и `31886`. Команда запускается из корня проекта.

```bash
node apps/api/test/recovery-drill.mjs
```

Проверка создаёт синтетические данные, переносит шифротекст и контрольную сумму, проверяет отказ при неверных сумме и ключе и восстанавливает чистую схему. Сценарий сверяет 12 таблиц, проверяет атомарность отказа при неверном списке администраторов, повторную подготовку и запуск с неверной версией. Проверяются старые и новые реквизиты, решения о доступе, результат известной команды, сохранённое закрытие и три запроса с неизвестным ключом, административная отмена, отметка счёта для сверки и возобновление графика. На выходе одна строка JSON с датами и замерами. Синтетические схемы и шифротекст остаются для разбора. Следующий запуск требует новые пустые схемы и каталоги.

## Результат локальной репетиции

13 ноября 2026 года по UTC на локальной OrbStack VM с Ubuntu 26.04, MySQL 8.4.13 и Node 26.13.1 сквозной прогон вернул `PASS`. Шифротекст и SHA-256 прошли путь VM → хост Mac → VM. Файл расшифровки оставался в отдельном каталоге VM. Проверки выполнялись через реальные процессы API и worker и два локальных HTTPS-порта Caddy.

| Событие | UTC |
| --- | --- |
| Точка перед началом снимка | `18:01:02.408` |
| Инцидент после блокировки, отзыва телефона, отмены автопроводки и ручной операции | `18:01:03.447` |
| Импорт и сверка 12 таблиц завершены | `18:01:04.561` |
| API доступен через HTTPS | `18:01:06.912` |
| Подтверждённый пользователь повторно вошёл с новой регистрацией | `18:01:07.598` |
| Worker провёл подтверждённую дату | `18:01:09.819` |

Синтетический RPO составил **1,039 с**, импорт со сверкой занял **1,114 с** после инцидента, синтетический RTO до первой подтверждённой проводки составил **6,372 с**. При проверке старых ключей осталось три движения. Четвёртое движение создал worker для проверенного правила владельца с сохранённой блокировкой входа. Удерживаемые и спорные даты остались без движений. Замеры относятся к синтетическому набору и имеющейся VM. Для рабочего запуска остаются отдельное внехостовое хранилище, проверка получения секретов при потере хоста, настройка расписания и оповещений и контрольный замер на целевом объёме данных.
